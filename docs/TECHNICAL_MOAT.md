# Technical moat — what is real, and what is not
**Implemented and tested (fixture-level):** (1) approval digests bound to target/params/amount/target-version and re-checked at dispatch; (2) write-ahead ledger + reconcile-by-lookup + restart recovery (never blind resend); (3) independent verifier per connector reading authoritative state; (4) task graph with dependency-gated writes and concurrent read-only tasks; (5) least-privilege agent roles where only the executor can dispatch; (6) mission revisions that preserve completed work and void stale approvals; (7) evidence model that refuses to treat an acknowledgement as proof; (8) ablations showing each control's measured cost (docs/VERIFICATION_EVIDENCE.md).
**Why it is hard to copy:** each connector needs a real *verification contract* against a system of record, and reconcile semantics depend on that provider's lookup/idempotency behaviour. Breadth of verified connectors compounds.
**Not a moat (be honest):** rule-based routing and the UI are easy to replicate; the benchmark is on our own fixtures; no proprietary data exists yet; live provider behaviour (timeouts, duplicate acks) is untested.
**What would make it real:** verified connectors to real airlines/hotels/CRMs, a corpus of real failure traces, and published live-provider reliability numbers.
