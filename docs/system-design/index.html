01

Rate Limiting

Partial

Problem. One bot sends 10,000 req/s and starves everyone else.

How it works. Count requests per key (IP or user) in a time window. Over the limit -> HTTP 429 plus Retry-After. Token bucket refills at a steady rate.

Takeaway. Limit at the edge (gateway/CDN), not in app code; always tell the client when to retry.

In REDEEM. app/core/security.py RateLimiter: sliding window per user/IP on login, register, missions, voice, cases, benchmark; 429 now returns Retry-After + retry_after_seconds (tests/test_auth_tenancy.py). Gap: process-local memory, not Redis/edge, so limits are per-instance (noted in DECISIONS.md).

02

Caching

Not Implemented

Problem. Identical expensive queries hammer the database.

How it works. Cache-aside: check cache, on a miss read the DB, write the result back with a TTL.

Takeaway. Cache only read-heavy, rarely-changing, expensive data. Always set a TTL. Never put sessions on a public CDN.

In REDEEM. No application cache layer. Only HTTP hints exist: Cache-Control private,max-age=60 on screenshots and no-store on the SSE stream (app/api/ops.py, app/api/missions.py). Tenant-scoped data is deliberately read live.

03

Load Balancing

Not Implemented

Problem. One server is a capacity limit and a single point of failure.

How it works. A balancer spreads requests (round robin) and health-checks nodes; a dead node stops receiving traffic.

Takeaway. Run >=2 instances behind a balancer with health checks before you need it.

In REDEEM. docker-compose.yml runs one api and one web container; no balancer. GET /health exists (app/api/misc.py) for a platform balancer to probe.

04

Reverse Proxy

Partial

Problem. App servers should not face the internet directly.

How it works. A proxy terminates TLS, compresses, serves static files and shields the backend.

Takeaway. Never expose Express/Django/Uvicorn on 80/443 directly.

In REDEEM. Next.js proxies /api to the API in compose (REDEEM_API_URL) and the API sets nosniff / no-referrer headers and X-Accel-Buffering for SSE. No TLS-terminating proxy is shipped; deployment is not configured.

05

API Gateway

Partial

Problem. Many services means many URLs and auth checks per client.

How it works. One entry point verifies the token once, rate-limits, routes, and forwards the identity downstream.

Takeaway. Validate the token once at the edge; pass the user id downstream.

In REDEEM. Single FastAPI service: session auth is validated once in a shared dependency and tenant_id comes only from the session (AGENTS.md rule 4; IDOR tests per resource). It is a modular monolith, so no separate gateway is needed or built.

06

CI/CD

Partial

Problem. It works on my machine, then breaks in production.

How it works. Every push builds and tests automatically; only green builds may be deployed.

Takeaway. AI-generated code never reaches users without a pipeline that runs tests and the build.

In REDEEM. .github/workflows/ci.yml runs sync_readme --check, ruff, pytest (api) and tsc, eslint, next build (web). CI only: there is no CD / deploy step.

07

Docker

Partial

Problem. Different OS and dependency versions behave differently.

How it works. Package code and dependencies into an image; run identical containers anywhere (shared kernel, lightweight).

Takeaway. Multi-stage build, small final image, run as non-root.

In REDEEM. apps/api/Dockerfile, apps/web/Dockerfile and docker-compose.yml (Postgres 16 + api + web) exist. The Docker build itself is untested: no Docker daemon in the build sandbox (AGENTS.md honest limits). Postgres 16 path was verified without Docker.

08

Kubernetes

Not Implemented

Problem. Who restarts crashed containers across many machines?

How it works. You declare the desired state (3 replicas); the control plane keeps reality equal to it and self-heals.

Takeaway. Do not adopt Kubernetes for an MVP. Use a PaaS until you have many services and an operator.

In REDEEM. Intentionally absent; the guide itself advises against it at this stage.

09

Service Discovery

Partial

Problem. Container IPs change constantly.

How it works. Internal DNS maps a stable name (auth-service) to the current healthy instances.

Takeaway. Address services by name, never by IP.

In REDEEM. Only docker-compose DNS names (api, db) are used. No dynamic discovery; there is one service.

10

Circuit Breaker

Implemented

Problem. A slow dependency drags its callers down with it (cascading failure).

How it works. After N consecutive failures the breaker opens and fails fast; after a cooldown it lets one probe through (half-open).

Takeaway. Degrade gracefully: return an empty list for non-critical features instead of crashing.

In REDEEM. app/voice/bolna.py CircuitBreaker (threshold 3, 30 s cooldown, half-open probe) guards the Bolna client and returns provider_circuit_open (503). Scope: the voice provider only; the Google adapter has none.

11

Timeouts

Partial

Problem. Waiting forever piles up connections and memory.

How it works. Every outbound call has a hard deadline; on expiry drop it and return an error.

Takeaway. No call without a timeout.

In REDEEM. Each persisted mission task has timeout_ms (default 10000) and a retry_budget (app/orchestration/taskgraph.py); the browser runner and provider clients take timeouts from config. Not audited as universal: new outbound calls must set one.

12

Retries

Partial

Problem. Transient faults (503, timeout) should not fail the user.

How it works. Retry only transient errors, never 4xx; cap attempts.

Takeaway. Max ~3 attempts, only on 5xx/timeouts, and only if the operation is idempotent.

In REDEEM. Read-only tasks carry a retry_budget; reconcile_action does up to 3 read-only lookups (engine.py). Writes are never auto-resent: an uncertain outcome is looked up, else sent to human review (AGENTS.md rule 5).

13

Exponential Backoff + Jitter

Not Implemented

Problem. Immediate retries from many clients become a self-inflicted DDoS.

How it works. Wait 1 s, 2 s, 4 s ... plus random jitter so clients do not retry in lockstep.

Takeaway. Backoff without jitter still synchronises clients.

In REDEEM. No backoff or jitter anywhere; reconcile_action states its backoff is a no-op for the in-process fixture. Needed before any real provider is called in anger.

14

Idempotency

Implemented

Problem. A retry after a dropped reply charges twice.

How it works. Client sends an Idempotency-Key; the server remembers it and returns the stored result instead of redoing the work.

Takeaway. Keys on every endpoint that moves money, sends email, or creates data.

In REDEEM. engine.py op_key() derives a deterministic idempotency_key per action; ProviderOperation rows record dispatches; verified actions are reused across revisions (ACTION_REUSED); reconcile-not-resend and restart recovery (recover_incomplete) are covered by the backend tests.

15

Queues + Dead Letter Queue

Not Implemented

Problem. Heavy work makes the user stare at a spinner.

How it works. The web tier enqueues a job and replies at once; workers drain the queue; jobs that keep failing park in a DLQ for inspection.

Takeaway. Queues are for async background work, not normal reads/writes.

In REDEEM. Execution is synchronous (AGENTS.md honest limits). The nearest analogue is escalation to human review for stuck actions; there is no queue, worker or DLQ. Next step recorded in IMPLEMENTATION_STATE.md: durable worker/outbox.

16

Pub/Sub

Not Implemented

Problem. Order service calling four systems directly is tightly coupled.

How it works. Publisher emits to a topic; any number of subscribers react independently and catch up after downtime.

Takeaway. Add a new consumer without touching the publisher.

In REDEEM. No broker. Missions append events to a per-mission ledger and /missions/{id}/stream serves them over SSE, which is a read stream for the UI, not inter-service pub/sub.

17

Event-Driven Architecture

Partial

Problem. Synchronous command chains break easily as systems grow.

How it works. Services broadcast immutable past-tense facts; others react. Needs distributed tracing (trace_id) to debug.

Takeaway. Name events in the past tense; carry a trace id.

In REDEEM. Append-only, sequenced ledger of past-tense events per mission (e.g. ACTION_REUSED, RECONCILED_FOUND); X-Request-ID correlation id in every error body (app/main.py). No bus, no cross-service tracing: it is one service.

18

Distributed Transactions

Implemented

Problem. A SQL transaction cannot span two databases.

How it works. Two-phase commit coordinates a commit across databases but is slow and holds locks.

Takeaway. Avoid them: design so one transaction touches one database.

In REDEEM. Avoided by design: one relational database, one transaction per state change. External systems are handled through connectors with idempotency + verify instead of 2PC.

19

Saga Pattern

Partial

Problem. Multi-step work across services needs undo when a step fails.

How it works. Chain local transactions; on failure run compensating transactions backwards. Accept eventual consistency and show 'Processing' states.

Takeaway. Design the UI for in-between states, not just Done.

In REDEEM. The engine orchestrates multi-step missions (flight_recovery: refund + hotel + calendar + draft + case) with per-step approval, verification and visible intermediate states. There are NO compensating transactions: a failed step goes to reconcile or human review rather than automatic undo.

20

Cron Jobs

Not Implemented

Problem. Some work must happen on a schedule, exactly once.

How it works. A scheduler enqueues jobs; a distributed lock or external orchestrator ensures only one instance claims each run. Store times in UTC.

Takeaway. Cron enqueues; it does not do the heavy work. Watch time zones.

In REDEEM. No scheduler. Only recover_incomplete() runs at startup (app/main.py lifespan). Timestamps use UTC (utcnow). With a single instance there is no duplicate-run risk yet; adding schedulers needs a lock first.
